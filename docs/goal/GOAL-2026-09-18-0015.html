產生時間:2026-09-18 00:15。接續 GOAL 7(A/B/C 完成,#11–#13 已關;C14 的時鐘問題與 #7 的 realtime 抖動留下來)。

使用者 2026-09-17 看完打滑的原因分析後定的範圍:四個方向全做。分析的結論(證據在 issue #1 的 GOAL 7 總結):

五條線(A 是其他線的前提)

A. 受控體物理化:打滑要算得出來,不是旗標指定

  1. 先實測,不要猜: - Isaac 場景裡輪子與地面實際生效的摩擦(ComputeBoundMaterial 查綁定、讀 frictionCombineMode,16 篇 §的做法),以及每個輪子實際的正向力(PhysX 接觸力或靜置時的支撐力)。 - DriveAPI 的 maxForce 在角向驅動的單位與實際飽和值(寫一個小場景量:擋住輪子,看關節扭矩)。 - 把「驅動扭矩上限 ÷ 抓地力扭矩」的實測比值寫進 38 篇,取代 GOAL 7 的推算 18 倍。
  2. 馬達改扭矩模型(三個受控體同一份公式,改公式三處一起改): - 扭矩 = f(duty, 轉速):至少含失速扭矩與反電動勢(τ = τ_stall × (duty − ω/ω_free));電流上限 = 扭矩上限。 - 輪子的牽引力上限 = μ × 正向力;超過就滑動,輪速與車速分開。 - 參數從一顆具體的小型減速馬達規格表抄(型號、版次寫進 36 篇),不要自己編。
  3. CONTACT=slip|freeze 拿掉:撞上之後打滑還是卡住,由扭矩與抓地力算出來。原本兩個場景的行為要能用參數重現(高摩擦 → 卡住、低摩擦 → 打滑),並在 38 篇寫明對應關係。
  4. 迴歸:末端位姿會變。新的參考值要與舊的並列,寫明「為什麼變」;C1–C15 全部重跑,判準本身不准動。

B. 韌體牽引力控制

  1. 設計先寫進 36 篇:SLIP 亮起後怎麼降(降 duty 斜率、限電流上限、回到多少),什麼條件解除。真板走得通的路徑,不准有模擬模式。
  2. 判準先寫進 38 篇:C16「打滑開始到輪子停之間,輪子比車體多走的距離 ≤ 上限」,上限從 A 線的物理參數推,寫明推法。
  3. 負對照 traction-off(偵測照亮、不降出力)要紅。
  4. 假受控體(--scene head-on)與 Isaac 都跑。

C. 上位脫困

  1. 現況:driver 收到 SLIP 鎖住、取消 goal,然後等人。
  2. 設計先寫進 38 篇 §6:收到 SLIP 之後後退固定距離、清 costmap、重新規劃、重送 goal;失敗幾次才放棄。
  3. C17:--scene head-on 或 blind-scan 場景下,上位最後把車開到 goal 0.1 m 內、途中不再撞;負對照 recover-off(維持 GOAL 7 的鎖住行為)紅。
  4. 與 C12(鎖住)不衝突:鎖住仍要成立,脫困是 ack 之後的事。

D. 預防碰撞

  1. 現況:保險桿是撞到才有;blind-scan 把雷射蒙住,所以撞得到。
  2. 做近距離安全區:雷射(或另一個近距離感測器)在設定距離內就減速、更近就停。要寫明 blind-scan 場景下這一條同樣無效(感測器被蒙住時沒有辦法),不要假裝解決了那個負對照。
  3. C18:沒有被蒙住的場景裡,車在障礙物前 X mm 停住、不觸發保險桿;負對照關掉安全區 → 撞到保險桿。
  4. 這一條的價值是「多一層」,不是取代 C11。

E. C14 的時鐘(GOAL 7 留下)

  • 現況:Nav2 用牆鐘(use_sim_time: false),lockstep 模擬比牆鐘慢,AMCL 的 map → odom 超過 DWB 的 transform_tolerance 0.3 s(量到差 0.31–1.23 s),C14 在高負載下五次紅三次(38 篇 §6.3)。
  • 做法:橋接發 /clock(Renode 虛擬時間)、ROS 那側 use_sim_time: true;掃描與 odom 的時間戳都改成模擬時間。
  • 判準不動:C14 照舊。要量的是「同一個負載下,改前紅幾次、改後紅幾次」(各五次)。
  • 不准只把 transform_tolerance 調大。

F. #7 的 realtime 抖動(優先序最低,閒時穿插)

  • 照 GOAL 7 D 線原本的做法:g_dbg 記韌體讀 CNT 的值與虛擬時刻,跟 ContinuousEncoder 的值逐筆對;同一個閒時視窗量 realtime 的 C13 誤報數。
  • C9 上限不准動;load < 6 才跑,每個數字附 uptime。
