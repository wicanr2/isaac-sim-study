四條線(A、C-1 不擋;B 先做離線分析;C-2 要重建映像;D 要場域主機)

A. realtime 的連續注入(#1 開放項,35 篇 §5.1 第 4 點)

量到的機制:編碼器 tick 由橋接在每步一口氣注入(cnt 直接寫 CNT),韌體在自己的 5 ms tick 讀 CNT。兩個節拍的比不是整數時,每個控制週期吃到的筆數會在 n 和 n+1 之間跳,C9 紅。lockstep --skew 表是決定性的重現。

  1. 先設計、寫下來再做。兩個候選: - (a) 每步把 Δtick 平均攤在該步 run_for 的虛擬時間上; - (b) 速度式:renode/hil_quadrature.cs 的 feeder 依受控體輪速,在 Renode 自己的虛擬時鐘上打邊緣,每步再用「受控體累計 tick − CNT」修正。

realtime 下橋接事先不知道 Renode 這一步會推進多少,(a) 可能只在 lockstep 成立。兩案的取捨寫進 37 篇 §3 再動手。 2. 判準先改、先寫死:C8(CNT == 受控體 tick)在連續注入下要換定義(例如「差 ≤ 一步的 tick 數,且每步結束時收斂」),改完寫進 38 篇 §1 再跑。C9 的上限不准動。 3. lockstep 迴歸:預設腳本在新注入法下的末端要報,跟 900.8 / 0.4 / 0.8627 並列。如果不一樣,先寫明哪個是新的參考值、理由是什麼,不能悄悄換參考值。舊的 cnt 注入保留成選項。 4. --skew 表加一欄(35 篇 §5.1)。預測,要量:比值不是整數的 uniform 列和兩列 stall 會轉綠;uniform:0.2 仍然紅,因為那一列的機制是迴路增益乘 5 之後 PI 自己振盪,跟注入法無關。量到的跟預測不一樣,就寫量到的,並找出原因。 5. realtime 閒時表:1 kHz 跑五次,新注入法 C9 要綠;同一個閒時視窗用 cnt 再跑一次當負對照,要紅。每個數字附 uptime。 6. 文件:35 §5.1 第 4 點最後的「兩個都還沒做」改寫成量測結果;37 §3 注入法表加一列;38 §5 失敗形態表的 realtime C9 列更新。

B. 打滑偵測(Isaac blind-scan 的「Nav2 假成功」,38 篇 §6.4 第 4 列)

現況:車撞上方塊以後,輪子頂著方塊打滑、編碼器照數,odom 一路走到 goal,Nav2 回 succeeded。真值離 goal 2.2 m、θ 差 0.75 rad。韌體的堵轉判斷看輪速,打滑時輪速正常,所以永遠不觸發。假受控體撞到就凍結編碼器,重現不了這個情況。

  1. 先離線分析,不寫程式。用 examples/hil-stm32/out/isaac_nav2_blind.csv(與 isaac_nav2_blind_cam.scan;檔案不在就重跑 WORLD=1 PLANT=remote UPPER=nav2 --negative blind-scan),在「打滑段」與「正常段」算三個候選訊號的分離度: - (a) 真值 yaw rate 對輪差 yaw rate,也就是理想陀螺儀看得到的差; - (b) 真值加速度對輪速微分,也就是理想加速度計看得到的差; - (c) 雷射對地圖的匹配殘差,或「odom 在前進、前方量到的距離不變」。

每個訊號報兩個數字:打滑開始後幾 ms 可判定;正常段(預設腳本、方形、Nav2 90 s 的轉向)誤報幾次。選方案前先有這張表。正面頂住、不轉向的打滑 (a) 看不到,表要能看出這一點。 2. 依表選方案: - 下位方案:在 Renode 加 IMU。先盤點 Renode 1.16.1 有哪些 I2C/SPI 慣性感測器模型,從原始碼或 monitor 列出來,不猜型號。韌體照資料手冊讀暫存器;三個受控體用同一份公式輸出角速度/加速度,雜訊用固定 seed;橋接寫感測器值的路徑比照其他週邊。 - 上位方案:雷射對地圖,與 C-2 的 AMCL 共用。 - 也可以兩個都做,但要寫明各自抓得到哪一種打滑。 3. 假受控體要能重現打滑(三個受控體同一份公式):加一個「接觸後輪子照轉、車體不動」的模式。沒有這個,負對照只能在場域主機上跑。 4. 新旗標或新行為先寫進 38 篇 §1.2 再做:旗標位元、亮起後韌體做什麼(停車或只回報)、driver 怎麼反應(比照 C12 鎖住)。 5. 判準 C13: - blind-scan 場景下,打滑在表上定的時間內被偵測到,Nav2 不得以 succeeded 收場; - 預設腳本、方形、Nav2 90 s 誤報 0 次; - 負對照 --negative slip-off 下 Nav2 又假成功,要紅。

假受控體與 Isaac 都要跑。

C. 重啟之後:IWDGRSTF 與重定位(38 篇 §1.2、§6.3)

C-1 Renode 的 RCC_CSR.IWDGRSTF - 現況:STM32_IndependentWatchdog 逾時會 RequestReset,但不設 RCC_CSR.IWDGRSTF(bit 29;原始碼裡有 TODO),所以韌體讀到的是重置值 0x0E000000。韌體 ctl_boot_detect()(firmware/control.c)照真板讀 RCC_CSR,讀完用 RMVF 清;因為 Renode 不設這個旗標,另外靠 .noinit 的 magic 判斷暖重置。 - 先讀 Renode 的 reset 流程再動手:RequestReset 會不會連 STM32F4_RCC 一起重置?會的話,旗標要放在重置流程之外才留得住,這是整個修正的核心。 - 修在 Renode,不改韌體的語意。做法比照前幾輪:fork 分支基於 master、commit 訊息英文、附 NUnit 測試,1.16.1 用執行期載入。上電、IWDG 重置、RMVF 三種狀態照 RM0090 §7.3.21。 - 判準: - --fault hang 之後 g_dbg.boot_csr 的 bit 29 是 1,上電那次沒有; - 新負對照 --negative noinit-off(韌體只信 RCC_CSR),修正後綠、stock 1.16.1 紅。 - .noinit 那條路保留,真板上兩條都成立。 - 上游:英文 PR 或 issue 的草稿給使用者看過才送。

C-2 AMCL 重定位 - 現況:重啟後 odom 歸零,driver 鎖住,等 /hil/fault_ack(C12)。map → odom 是靜態 identity,ack 之後仍然是錯的。 - hil-nav2:jazzy 沒有 AMCL(ros/Dockerfile.nav2 的套件清單裡沒有 ros-jazzy-nav2-amcl)。重建映像前先報大小增量再問。 - 先查風險:world.json 的房間是 4 × 3 m 的矩形,只畫牆的地圖有 180° 旋轉對稱,AMCL 可能收斂到鏡像解。可以用 tools/gen_map.py --boxes 把方塊畫進地圖來打破對稱,但那會動到 blind-scan 負對照的前提(方塊本來是「地圖上沒有、只有雷射看得到」)。先量對稱會不會真的出事,再決定怎麼改,兩個負對照都要保住。 - 流程:重啟 → 鎖住 → AMCL 收斂(協方差門檻寫死)→ 解鎖 → 重送 goal → 到達。 - 判準 C14:UPPER=nav2 --fault hang - 解鎖前 C12 仍成立; - 最後到 goal 0.1 m 以內、碰撞 0; - 負對照 --negative static-map-odom(ack 後照舊用 identity)從錯的起點規劃,要紅。
